# Velora — торговый бэкенд

Бэкенд демо-платформы: аутентификация, реальные котировки, торговый движок, леджер и админка с аудитом.

## Запуск

```bash
cd server
npm install
cp .env.example .env      # обязательно поменяй секреты
npm run seed              # создаёт БД, инструменты и двух пользователей
npm run dev               # http://localhost:4000
```

Проверка, что всё живо (в отдельном терминале, сервер должен быть запущен):

```bash
npm run smoke             # 60 проверок сквозного сценария
```

### Ключевые решения

**Деньги — целые числа.** Все суммы, цены и количества хранятся как `BigInt`, масштабированные на 1e8. Ни один баланс не проходит через `float`: `0.1 + 0.2` в деньгах недопустимо.

**Леджер как источник истины.** Баланс меняется только через `postLedger()`, который в той же транзакции пишет неизменяемую запись в журнал. Баланс любого счёта восстанавливается суммированием его записей — это делает возможным сверку и разбор инцидентов.

**Синхронные транзакции.** `better-sqlite3` синхронный, поэтому транзакцию физически нельзя разорвать другим `await`. Деньги перемещаются целиком или не перемещаются вовсе.

**Движок на сервере.** Лимитные ордера, стопы и ликвидации срабатывают в серверном цикле каждые 2 секунды — независимо от того, открыта ли у трейдера вкладка.

**Что происходит, когда котировки недоступны.** Символ, у которого нет котировки или котировка старше `MAX_QUOTE_AGE_MS` (по умолчанию 2 минуты), считается **остановленным**: по нему ничего не открывается, не закрывается, не исполняется и не ликвидируется, пока не придёт свежая цена. Альтернатива — продолжать работать по последнему известному числу — хуже сразу в обе стороны: трейдер получает исполнение по цене, которую рынок прошёл минуты назад, и, что куда серьёзнее, позиции ликвидируются по цене, которой не было. Остановка симметрична намеренно: во время неё нельзя ни выйти из позиции, ни отобрать её. Единственное определение «слишком старая» живёт в `quoteIsFresh()` (`engine/prices.ts`) и используется и в `engine/execution.ts`, и в `engine/matching.ts`. `/api/instruments` отдаёт по каждому инструменту флаг `tradeable`, а `/api/health` — состояние фида, так что интерфейс показывает последнюю известную цену и честно говорит, что торговля приостановлена.

**Второй фактор.** TOTP по RFC 6238 со стандартными параметрами (SHA-1, 6 цифр, шаг 30 с) — иначе секрет просто нечем отсканировать. Общий секрет хранится **зашифрованным** (AES-256-GCM, ключ в `ENCRYPTION_KEY`, не в базе), а не хешированным: сервер обязан прочитать сами байты, чтобы посчитать текущий код, и дамп базы без ключа при этом бесполезен. Пароль при включённой 2FA даёт только пятиминутное окно, в котором нужно подтвердить второй фактор: токен этого окна подписан тем же ключом, что и access-токен, поэтому `plugins/authenticate.ts` отклоняет его явно — иначе двухфакторка была бы декоративной. Резервные коды одноразовые и хранятся как SHA-256: у них ~50 бит энтропии, защищать bcrypt тут нечего, а десять сравнений bcrypt на каждую попытку входа — это уже свой собственный отказ в обслуживании.

**Ссылки из писем.** Подтверждение почты и сброс пароля — одна таблица `auth_tokens` и один путь: хранится только SHA-256 токена, выдача новой ссылки гасит предыдущие, а погашение атомарное (`UPDATE ... RETURNING`), так что два одновременных перехода по одной ссылке не могут выиграть оба. `/forgot-password` отвечает одинаково для существующего и несуществующего адреса — иначе это публичный оракул, показывающий, у каких почт есть деньги на платформе.

**KYC.** Документы и селфи лежат в **приватном** бакете Supabase Storage. В базе хранится не URL, а путь к объекту: паспорт, доступный по ссылке, — ровно та ошибка, ради предотвращения которой всё это и устроено. Наружу документ попадает только через подписанную ссылку на несколько минут, и только когда админ реально открыл конкретную заявку — список очереди не содержит ссылок вообще, иначе один запрос страницы порождал бы десятки живых ссылок на чужие паспорта. Каждый просмотр документов пишется в аудит: «кто и когда смотрел этот паспорт» — вопрос, который рано или поздно задают. `kyc_submissions` — это история, а не одна строка на пользователя: причина отказа должна быть читаема и после повторной подачи. Решение проводится через `UPDATE ... WHERE status = 'PENDING' RETURNING`, так что два админа не могут одновременно вынести разные вердикты. Если бакет не настроен, подача заявки отклоняется явно — принять чужой паспорт и не иметь места, куда его безопасно положить, хуже, чем отказать.

**Что закрыто за верификацией.** Только вывод средств и накопительные счета. Пополнение и внутренние переводы намеренно не закрыты: запрещать человеку *вносить* деньги или двигать их между своими счетами — это трение без выигрыша в уверенности.

**Накопительные счета.** Тело вклада лежит в `savings_accounts`, деньги, из которых он пополнен, — там же, где всегда, в `accounts.cash_scaled`, а каждый перевод между ними — строка в `ledger_entries`. Ни одна из сторон не может разъехаться с другой. Проценты начисляются **за целые прошедшие сутки** и считаются от собственного `last_accrual_at` счёта, а не от того, какой тик сейчас выполняется: выплата зависит от времени, а не от аптайма — сервер, простоявший двое суток, доплатит за оба дня, а тик, случайно выполнившийся дважды, не заплатит дважды. Проценты идут на **основной баланс**, а не в тело вклада: так журнал остаётся единственным источником истины по деньгам, а доход по срочному вкладу можно тратить, пока сам вклад ещё заблокирован. Ставка считается одним целочисленным делением `баланс × APY / 36500`, а не через заранее округлённую дневную ставку — округление до восьми знаков забирает ~0.002% каждой выплаты, что незаметно за день и заметно за год на всех счетах сразу.

**Мониторинг.** `lib/monitoring.ts` — сбор ошибок (Sentry) и операционные алерты. Необязателен: без `SENTRY_DSN` всё работает так же, а ошибки идут только в лог. В трекер не попадают тела запросов, cookie и заголовки авторизации — только форма сбоя. Фид цен эскалируется сам: первый неудачный цикл — строка в логе, непрерывный сбой дольше `FEED_UNHEALTHY_ALERT_MS` (по умолчанию минута) — один алерт на весь инцидент, плюс один при восстановлении.

**Боты — тоже на сервере.** GRID и MARTINGALE раньше крутились в браузере (`frontend/src/lib/strategyEngine.ts`): бот торговал только с открытой вкладкой, перезагрузка могла молча перезапустить его, а две вкладки запускали одного и того же бота дважды. Теперь `engine/strategy.ts` шагает каждым RUNNING-ботом в собственном серверном интервале и вызывает те же `placeOrder()` / `closePositionById()` из `engine/execution.ts` — внутрипроцессно, без HTTP-запросов сервера к самому себе. Таблица `bots` хранит `config` (что задал пользователь, неизменно) отдельно от `state` (что бот успел сделать), `bot_logs` — журнал его действий.

**Котировки с сервера.** Внешние API вызывает бэкенд: нет CORS-проблем, лимиты запросов централизованы, будущий API-ключ не утечёт в браузер, и все клиенты торгуют против одной цены. Инструменты без бесплатного фида (CFD) помечены `source: SYNTHETIC` — модельное число никогда не выдаётся за реальную котировку.

**Безопасность.** Пароли — bcrypt (12 раундов). Refresh-токены хранятся хешированными и ротируются при каждом использовании; повторное предъявление отозванного токена рвёт все сессии пользователя. Заблокированный аккаунт теряет доступ немедленно, а не по истечении токена. Внутренние ошибки не утекают клиенту.

## API

### Публичные
```
GET  /api/health
GET  /api/instruments
GET  /api/instruments/:symbol/candles?tf=15m|1H|4H|1D|1W
WS   /ws/prices
```

### Аутентификация
```
POST /api/auth/register        { email, password, name? }
POST /api/auth/login           { email, password }
POST /api/auth/refresh
POST /api/auth/logout
GET  /api/auth/me
POST /api/auth/change-password { currentPassword, newPassword }
```

### Торговля (Bearer-токен)
```
POST   /api/orders             { symbol, side, type, qty, price?, leverage?, takeProfit?, stopLoss? }
GET    /api/orders?status=NEW|FILLED|CANCELLED|ALL
DELETE /api/orders/:id
GET    /api/positions
PATCH  /api/positions/:id      { takeProfit?, stopLoss? }
POST   /api/positions/:id/close
GET    /api/trades
GET    /api/account
GET    /api/ledger
GET/POST/DELETE /api/alerts
```

### Админка (роль ADMIN)
```
GET    /api/admin/stats
GET    /api/admin/users?search=&status=&page=&pageSize=
GET    /api/admin/users/:id
PATCH  /api/admin/users/:id                              { name?, status?, role? }
POST   /api/admin/users/:id/balance                      { amount, note? }
POST   /api/admin/users/:id/reset-password               { newPassword }
POST   /api/admin/users/:uid/positions/:pid/close
DELETE /api/admin/users/:uid/orders/:oid
GET    /api/admin/audit?action=&targetUserId=
PATCH  /api/admin/instruments/:symbol                    { active?, maxLeverage? }
```

Суммы во всех ответах — строки (`"9222.31"`), чтобы точность не терялась при JSON-сериализации. Отправлять их обратно нужно тоже строками.

## Перед продакшеном

Это демо-платформа с виртуальными деньгами. Если появятся реальные средства, обязательны:

- PostgreSQL вместо SQLite (SQL портируемый, но нужны миграции и репликация)
- HTTPS и `secure`-куки (`NODE_ENV=production` включает это автоматически)
- Реальный market-data провайдер по договору вместо публичных бесплатных API
- 2FA, KYC/AML-процедуры, регуляторные требования вашей юрисдикции
- Внешний мониторинг, алертинг и регулярная сверка леджера с балансами
- Нагрузочное тестирование движка и вынос его в отдельный процесс
